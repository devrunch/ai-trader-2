## Goal
Fix four problems found by running the system against live Kite during NSE hours on 2026-11-09. **Make no real Kite, Deriv or Yahoo calls in this task**: tests use fakes only. Zerodha is currently rejecting scripted logins, so don't start the market-data process with real credentials.

## SRD

## Findings and required fixes
1. **The real failure was hidden.** `ResilientFeed` logged only `feed connection failed`. The real cause, a Kite login rejected at stage `login`, was invisible.
   - When the transport factory or connect throws, log a **safe** summary: the error class name, and for `KiteLoginError` its `stage` and `message`. Credentials never appear in those, by P1-3's design; keep it that way.
   - Map a `KiteLoginError` to feed state `stale` with reason `AUTH_EXPIRED`, not `PROVIDER_DOWN`. Clients then see "login problem", not "vendor down".
   - Test: `logs the login stage and maps login failure to stale AUTH_EXPIRED`.
2. **Login attempts must be strictly bounded** (this protects the Zerodha account).
   - Across the whole process, the Kite session must never attempt more than **3 logins per 15 minutes, and never more than 6 per day**. Persist the attempt count per day in Postgres (`vendor_sessions` gets `login_attempts_day date` and `login_attempts int`, plus a migration) so restarts don't reset it.
   - Beyond the cap, `getAccessToken` throws `UnavailableError` with `details: { reason: 'login attempts exhausted', retryAt }`, with no network call.
   - Tests: `caps logins at 3 per 15 minutes and 6 per day across restarts`; `exhausted logins make no network call`.
3. **Concurrent instrument refreshes.** The bootstrap `runNow` and a manual `RefreshInstruments.execute` ran together and one source failed with "transaction failed". `RefreshInstruments.execute` must hold a Redis lock (`lock:instruments-refresh`, `SET NX PX` 15 min, compare-and-delete on release).
   - A concurrent call waits up to 60 s for the running refresh and then returns that refresh's report. It never starts a second one.
   - Test (integration, Redis plus Postgres): `concurrent refreshes run once and both callers get the report`.
4. **Held continuous instruments.** The popular list held by the market-data supervisor includes `MCX:GOLD1!`, `NSE:NIFTY1!` and others. The supervisor passed them to the feed as they were, and the feed couldn't map them.
   - Resolve continuous IDs through `ResolveInstrument` to their dated contract before subscribing, and re-resolve daily at the IST date change (cron `5 0 * * *` via `JobScheduler`). When the contract rolls, unsubscribe the old one and subscribe the new one.
   - Test: `held continuous ids subscribe their dated contract and roll at the date change`.
