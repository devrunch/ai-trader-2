## Interfaces (exact)
```ts
export interface JobSpec {
  name: string;               // unique, kebab-case
  cron: string;               // 5-field cron
  tz: string;                 // IANA zone, e.g. 'Asia/Kolkata'
  maxRuntimeMs: number;       // run aborted via signal after this
  graceMs: number;            // a run missed by downtime is caught up if now - scheduledAt <= graceMs
  run(signal: AbortSignal): Promise<void>;
}
export interface HeartbeatSink { beat(job: string, outcome: 'ok' | 'failed' | 'skipped', detail?: string): Promise<void> }
export const HEARTBEAT_SINK: symbol;        // default provider: a no-op sink that logs at debug
export class JobScheduler {
  register(spec: JobSpec): Promise<void>;   // idempotent: upsertJobScheduler(name, { pattern: cron, tz }, …); re-register with a changed cron updates it
  runNow(name: string): Promise<void>;      // enqueue one immediate run (deduplicated: a second runNow while one is queued or active is a no-op)
  lastRun(name: string): Promise<{ at: string; outcome: 'ok' | 'failed' | 'skipped' } | null>;
}
// pure helper, exported for the unit tests:
export function missedRunDecision(lastScheduledAt: Date | null, previousFireAt: Date, now: Date, graceMs: number): 'run' | 'skip' | 'none';
```

## Behaviour
- **One queue per job:** `jobs:<name>`, with a Worker at concurrency 1. A Redis-backed lock (BullMQ handles it at concurrency 1 and one worker per process; also guard with a `SET NX PX` key `jobs:<name>:lock`, TTL = `maxRuntimeMs` + 30 s) stops two API instances running the same job at once.
- **Timeouts:** each run gets an `AbortController`. At `maxRuntimeMs` the signal aborts, the run is marked `failed` with `detail: 'timeout'`, and the lock is released.
- **Errors:** a throwing `run` gives `failed` with the error message (≤ 200 characters). The worker carries on with the next schedule.
- **Catch-up on startup:** for each registered job, compute the previous fire time from the cron in `tz`. If the job's last recorded run (`lastRun`) is older than that time:
  - within `graceMs`: run once now (`'run'`);
  - beyond `graceMs`: log `skipped` (`'skip'`) and heartbeat `skipped`.

  Use `cron-parser` (latest, exact) for the previous fire time; BullMQ already depends on it.
- **Run records:** each finished run writes `jobs:<name>:last` = JSON `{at, outcome}`, and calls `HeartbeatSink.beat`.
- **Shutdown:** `onModuleDestroy` closes the workers gracefully, waiting for active runs up to 10 s, then aborts them.
- **No job is registered in this task.** P1-3 and P1-5 register theirs.

## Tests to write first
**`job-scheduler.spec.ts`** (pure):
- `missedRunDecision runs a run missed within grace`;
- `missedRunDecision skips a run missed beyond grace`;
- `missedRunDecision is none when the last run covers the previous fire time`.

**`jobs.int-spec.ts`** (real Redis container; use a cron of every second via `*/1 * * * * *` in a 6-field form if BullMQ accepts it, or call `runNow` to drive runs, keeping tests under 30 s total):
- `runs a registered job on schedule`;
- `never runs two copies of one job` (two `JobScheduler` instances, as two app instances on one Redis; a job that takes 1.5 s; concurrent triggers give exactly one run at a time — track max concurrency = 1);
- `aborts a job at maxRuntimeMs` (it records `failed` with `timeout`, and the signal was aborted);
- `a throwing job records failed and the next run still happens`;
- `catches up a run missed within grace after restart` (seed `jobs:<name>:last` to before the previous fire time; on registration it runs once);
- `skips a run missed beyond grace and heartbeats skipped`;
- `re-registering the same job does not duplicate it` (`getJobSchedulers` count stays 1);
- `runNow while a run is active is a no-op`.
