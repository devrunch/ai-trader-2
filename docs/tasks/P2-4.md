# Task P2-4: Kite history, read-through and nightly backfill

Read `AGENTS.md` first. It's binding. Do only what this brief asks. Plan § P2-4.

## Goal
History for Indian instruments comes from Kite into the candle store:
- **on demand:** when a read finds no older data;
- **nightly:** for the held universe, reconciling live-built bars against Kite's own history (vendor wins, marked repaired).

All of it goes through a typed provider port and a shared, cross-process rate limit.

## SRD
FR-MD-1 (provider port; data **or** a typed reason, never `null`), FR-MD-2 (backfill and reconcile), FR-MD-4 (about 3 history requests per second, shared limiter), E3 (an expired token is reported), E4 (429 → queue, no tight retry loop), E6 (breaker, then `PROVIDER_DOWN` fast).

## Kite history adapter rules
- **Call:** `kiteconnect` `getHistoricalData(instrument_token, interval, from, to)`, using intervals `minute` and `day` only (we aggregate everything else).
  - **Chunking:** at most 60 days per `minute` request and 2,000 days per `day` request; chunks run in order, each taking a token from the shared bucket `rl:kite:history` (capacity 3, refill 3/s).
  - **Bar times:** Kite returns bar *start* times in IST, so convert to epoch ms UTC.
  - **Volume:** a real number for equities and futures. For indices, Kite returns 0, so store `null` ("not counted", never 0).
- **Errors map to reasons:**
  - `TokenException` → `AUTH_EXPIRED`;
  - HTTP 429 or `NetworkException` with "Too many" → `RATE_LIMITED`, with `retryAfterMs` 1000;
  - another network error or 5xx → `PROVIDER_DOWN`;
  - `InputException` for an unknown instrument → `UNSUPPORTED`;
  - an empty result → `NO_DATA`.
- **Breaker:** a `CircuitBreaker({ failureThreshold: 3, openMs: 60_000 })` wraps the calls. When it's open, return `PROVIDER_DOWN` with `retryAfterMs` immediately. `NO_DATA` and `UNSUPPORTED` don't count as failures.
- **Timeout:** each request has a 15 s timeout, and the caller's signal is honoured.
- **No vendor substitution:** the Kite provider never falls back to another vendor (E3).

## FillHistory rules
- **Routing:** resolve the instrument's mapping for its provider (`kite` for NSE, BSE, MCX and NFO instruments). No mapping → `{ ok:false, reason:'UNSUPPORTED' }`.
- **Single-flight:** one in-flight fill per `(instrumentId, res, from, to)` per process; concurrent callers share it.
- **Store:** results go into `upsert1m` or `upsert1d` with source `kite`.
- **Continuous IDs** (`…1!`): out of scope for history splicing. Return `UNSUPPORTED` with `detail: 'continuous history arrives in P2-8'`.

## ReadBars change
When `complete === false`, call `FillHistory` for the missing window *once* (1m for intraday intervals, 1d for daily and higher), then re-read. Return the page plus `status`:
- `ok` when data was there or was filled;
- `'stale'` with the provider reason when the fill failed and some bars exist;
- a `ProviderResult` failure when there are no bars at all.

Add the field `status: { ok: true } | { ok: false; reason: ProviderReason; detail?: string }` to `BarsPage`.

## BackfillHeld rules (job `bars-backfill`, cron `30 0 * * *`, IST, `graceMs` 6 h, `maxRuntimeMs` 45 min)
- **The held universe:** active instruments from the P1-6 popular list that map to Kite. Watchlists are added in a later phase.
- **For each instrument:** fetch the last 5 trading days of `minute` and the last 400 days of `day`, then `mergeRepair` against the stored bars and upsert. Log the counts per instrument (written and repaired) at `info`.
- **Isolation:** one failing instrument never stops the rest.
