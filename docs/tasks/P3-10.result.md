# P3-10 Result: "no data" on Monday mornings and for US stocks

## Bugs
1. **Monday morning or after a holiday, a symbol with nothing stored read as "no data" (any exchange).** A latest read filled only its estimated window (about one day for small pages), which held no session. Latest reads with an empty store now reach back at least 7 days.
2. **US: a 1-minute range older than 30 days was refused entirely.** Yahoo keeps about 30 days, so a 1h chart (500 bars, about 77 days back) got nothing. The range is now clamped to the last 29 days; only a range entirely older than that is "no data", without calling Yahoo.

## Tests
- `with nothing stored, the first fill reaches back past a weekend (Monday morning, new symbol)`: RED, then GREEN.
- `a minute request older than Yahoo keeps is clamped to the last 30 days, not refused`: RED, then GREEN.
- The old "refuse at 30 days" test was rewritten to the intended rule: an entirely-old range gets no call.
- `since` reads are unchanged (they ask for bars from a time on).

## Added: leader lease survives a slow Redis (live finding 2026-11-10)
- **What happened:** during the forex live test, Redis calls timed out under heavy machine load. The market-data leader treated one timed-out renew as "lost", stopped every feed twice in 30 s, and FX:EURUSD lost the minute 06:17 UTC.
- **`LeaderLock`:** keeps leadership through transient errors while its lease is known valid (send time + TTL − 1 s). It gives up when Redis names another holder or the lease has run out. New method `holdsLease()`.
- **The persistence fence** now uses `lock.holdsLease()` instead of reading `md:leader` from Redis every second, so a slow Redis never drops a bar. This stays safe: no other instance can acquire before our lease expires in Redis (NX), and the local deadline is earlier than the real expiry.
- **Tests:** two new lock tests (RED, then GREEN). The market-data process integration tests (7) pass, including "a deposed leader stops writing bars".
