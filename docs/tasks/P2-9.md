# Task P2-9: Market-data process with leader lock

Read `AGENTS.md` first. It's binding. Do only what this brief asks. Plan § P2-9.

## Goal
A second entrypoint in the same codebase runs only the vendor feeds (Kite, Deriv, US delayed) and the bar pipeline:
- under a Redis leader lock, so exactly one process holds vendor sockets even during a rolling deploy;
- publishing per-vendor feed state for the API (`md:feed-state:<vendor>`);
- serving subscription requests from the API through Redis;
- flushing forming bars on shutdown.

A standby takes over within 15 s if the leader dies.

## SRD
§10.5 (one market-data writer, leader lock), FR-MD-5 (subscribe on demand, 60 s grace), NFR-RB-7 (graceful shutdown), NFR-RB-8, E16 (restart rebuilds), E25 (a deploy never loses the feed for long).

## Interfaces you produce (exact)
```ts
export class LeaderLock {               // Redis key `md:leader`, value = instance id
  constructor(redis: Redis, instanceId: string, opts?: { ttlMs?: number /* 10_000 */; renewMs?: number /* 3_000 */; clock?: () => number });
  acquireLoop(signal: AbortSignal, onAcquired: () => Promise<void>, onLost: () => Promise<void>): Promise<void>; // tries SET NX PX every renewMs; renews with a compare-and-pexpire Lua script; on renew failure → onLost
  release(): Promise<void>;             // compare-and-del
}
export class FeedSupervisor {           // runs only while leader
  constructor(deps: { feeds: LiveFeed[]; liveBars: LiveBars; publisher: FeedStatePublisher; requests: SubscriptionRequests });
  start(): Promise<void>;               // attach LiveBars, start feeds, publish state on every change, apply current subscription set
  stop(): Promise<void>;                // flush forming bars (LiveBars closeDue(now) then persist), stop feeds, publish 'stopped'
}
export class FeedStatePublisher { publish(vendor: FeedVendor, state: FeedState, reason?: ProviderReason): Promise<void> } // SET md:feed-state:<vendor> JSON, PX 60_000, refreshed every 20 s while leader
export class SubscriptionRequests {    // Redis hash `md:subs` field=instrumentId value=refcount; channel `md:subs:changed`
  current(): Promise<Map<string, number>>;
  onChange(cb: (instrumentId: string, count: number) => void): () => void;
}
export class RequestSubscription {     // API side
  acquire(instrumentId: string): Promise<void>;   // HINCRBY +1, publish change
  release(instrumentId: string): Promise<void>;   // HINCRBY -1 (floor 0, delete at 0), publish change
}
```

## Rules
- **Routing:** the supervisor routes each instrument to its vendor feed by exchange (the same table as `MarketDataService`; move that table into one shared function in `application/vendor-for.ts` and use it in both places, so it isn't duplicated).
  - A count rising from 0 → `feed.subscribe([id])`.
  - A count dropping to 0 → `feed.unsubscribe([id])`. The feed's own 60 s grace applies.
- **Held instruments:** the popular list (from the instruments application API) is always subscribed while leader, as a held set with a count of 1, separate from requests.
- **Losing leadership:** stop the feeds within 2 s; never run two leaders. Use a fencing check: every `LiveBars` persist path first checks `md:leader === instanceId` (cheap `GET`, cached 1 s) and skips writes when it's no longer leader.
- **Shutdown** (SIGTERM or SIGINT): `supervisor.stop()`, then `lock.release()`, then close the app. All within 20 s (NFR-RB-7).
- **Restart (E16):** `LiveBars` already restores from `FormingBarStore`; the supervisor must not clear forming bars on start.
- **Deriv Friday follow-up (from P2-6):** Deriv FX and metals stop around 20:54 UTC on Friday, but the FX calendar closes at 22:00 UTC. Give the feed's watchdog a per-vendor quiet window: for `deriv`, skip the watchdog from Friday 20:50 UTC to the FX close. Add the test `deriv watchdog does not fire in the Friday quiet window`.
