# Task P1-3: Kite session

Read `AGENTS.md` first. It's binding. Do only what this brief asks.

## Goal
The API mints and keeps a valid Kite Connect access token on its own:
- a scripted login (password + TOTP), then the official token exchange;
- the token stored in Postgres, reused until Kite's daily 06:00 IST expiry;
- a fresh token minted each day at 06:20 IST, with catch-up after downtime;
- a circuit breaker on minting;
- `/ready` reports whether a valid token exists.

Credentials never appear in logs, errors or responses.

## SRD
FR-MD-3 (Kite session renewed before expiry), E3 (token expired or login failed → retry with backoff, report it, recover by itself), NFR-SC-1 (no secrets leaked), NFR-RB-2 (circuit breaker), NFR-RB-5 (durable job). Plan: `docs/superpowers/plans/2026-11-08-phase-1-instruments.md` § P1-3.

## Interfaces (exact)
```ts
export interface KiteCredentials { apiKey: string; apiSecret: string; userId: string; password: string; totpSecret: string }
export type KiteLoginStage = 'login' | 'twofa' | 'redirect' | 'session';
export class KiteLoginError extends Error { constructor(readonly stage: KiteLoginStage, message: string) } // message never contains credential values
export interface KiteHttp { request(url: string, init: { method: 'GET' | 'POST'; form?: Record<string, string>; signal: AbortSignal }): Promise<{ status: number; headers: Headers; json(): Promise<unknown>; url: string }> }
export function createKiteHttp(): KiteHttp; // undici, no automatic redirects, cookie jar across calls, 15 s timeout per call
export async function loginToKite(creds: KiteCredentials, http: KiteHttp, signal: AbortSignal, now?: () => number): Promise<{ requestToken: string }>;
export interface KiteTokenExchange { generateSession(requestToken: string, apiSecret: string): Promise<{ access_token: string; user_name?: string }> }
export class KiteSessionService {
  getAccessToken(signal?: AbortSignal): Promise<string>;   // stored valid token or a single-flight mint
  refresh(signal: AbortSignal): Promise<void>;              // force mint (used by the job)
  status(): Promise<{ valid: boolean; expiresAt?: string; reason?: string }>;
}
export function nextKiteExpiry(mintedAt: Date): Date; // the next 06:00 Asia/Kolkata strictly after mintedAt
```

## Login flow (mirror of the proven Python implementation in the old project)
1. **Login:** `POST https://kite.zerodha.com/api/login`, form `{ user_id, password }`. Expect 200 JSON `{ data: { request_id } }`. Anything else → `KiteLoginError('login', …)`.
2. **Two-factor:** `POST https://kite.zerodha.com/api/twofa`, form `{ user_id, request_id, twofa_value: <TOTP now>, twofa_type: 'totp' }`. Expect 200 → otherwise `KiteLoginError('twofa', …)`.
3. **Redirect walk:** `GET https://kite.zerodha.com/connect/login?api_key=<key>&v=3` **without** following redirects. Walk `Location` headers by hand, up to 10 hops. Stop at the first `Location` (or response URL) containing `request_token=`, and extract the value up to `&`. If none appears → `KiteLoginError('redirect', 'no request_token')`. The registered redirect URL itself is never fetched.
4. **Token exchange:** `KiteTokenExchange.generateSession(requestToken, apiSecret)`. The real implementation wraps `kiteconnect`'s `KiteConnect({ api_key }).generateSession`. Failure → `KiteLoginError('session', …)`.

## Storage and service rules
- **Table** `vendor_sessions`: `vendor text primary key`, `access_token text not null`, `minted_at timestamptz not null`, `expires_at timestamptz not null`. Upsert on `vendor = 'kite'`.
- **`getAccessToken`:** returns the stored token while `now < expires_at - 60 s`; otherwise it mints. Concurrent callers share one in-flight mint (single-flight).
- **Mint:** login, then exchange, then store with `expires_at = nextKiteExpiry(now)`, all inside a `CircuitBreaker({ failureThreshold: 3, openMs: 15 * 60_000 })`. An open breaker gives `UnavailableError` with `PROVIDER_DOWN`-style details `{ vendor: 'kite', retryAfterMs }`.
- **No credentials:** `getAccessToken` throws `UnavailableError` with a `reason: 'kite credentials not configured'` detail.
- **Job:** `kite-session-refresh`, registered with `JobScheduler` (P1-2): cron `20 6 * * *`, tz `Asia/Kolkata`, `graceMs` 6 h, `maxRuntimeMs` 120 s; it calls `refresh`. Register it only when credentials are configured.
- **Readiness `kite`:**
  - `up` when the stored token is valid;
  - `down` with `reason: 'no valid token'`, `'credentials not configured'`, or the breaker reason.

  It must never mint inside the readiness check.
- **Logs:** say "Kite session minted, expires <iso>". Never the token; never a credential.

## Tests to write first

- `expiry is the next 06:00 IST` (minted 2026-11-08T05:59 IST → 06:00 the same day; minted 06:20 → 06:00 the next day);
- `opens the breaker after 3 failed mints and fails fast with retryAfterMs`;
- `readiness reports down without minting when no token exists`;
- `throws credentials not configured when config lacks them`.
